# 瑶光台重构设计方案 v2

日期为 2026-11-04。本文保留为早期设计参考，后续项目范围、优先级和实施路线以 [项目规划与开发计划 v3](项目规划与开发计划-v3.md) 为准，实际完成情况见 [重构开发进度](重构开发进度.md)。

新版将 YPKG 完善和插件化系统能力列为核心交付。本文关于原生插件首期范围的取舍、P0 至 P4 排期及实施前现状描述，均按历史背景理解。

本方案依据当前 README、应用管理、YPKG、CEF 桥接、窗口、资源加载和存储代码编写。现状判断来自静态阅读，未进行构建、运行或设备验证；当前 tests 目录未发现可读取的测试页面文件。以下接口、目录、性能指标和排期均是设计建议，不代表现有功能。

## 1. 产品定位与核心结论

**瑶光台是 Windows 上托管前端应用、统一提供受控系统能力的桌面运行平台。**

用户安装一个瑶光台，再安装多个前端应用。应用开发者负责页面、交互、界面状态和业务流程编排，通过统一 SDK 使用系统能力；平台负责安装、身份、授权、文件、网络、存储、窗口和生命周期。

“前端只关注 UI”不应解释成把每个业务规则都搬进瑶光台 C++。表单校验、页面状态、业务 API 的组合仍属于应用；操作系统访问、凭据保管、持久化和执行权限属于平台。瑶光台不内置聊天、财务、订单等具体业务，也不执行包里任意附带的本机程序。

建议采取以下基线：

1. 保留 C++20、CEF 和 Windows x64 方向，重建架构和协议，不沿用旧代码结构作为约束。
2. 平台核心采用模块化单体；CEF 保持多进程，首期不另造复杂后台服务体系。
3. 前端使用框架无关的 TypeScript SDK；平台桌面自身也是受管理的前端应用。
4. 静态资源协议与系统调用桥接分离。`alkaid://` 专注应用资源，SDK 负责系统操作。
5. 应用身份、授权、数据和生命周期由宿主统一管理，前端传入的身份字段不作为信任依据。
6. 开发工具与用户运行时分离。构建、打包、签名在开发端完成；运行时只验包、安装和运行。
7. 采用新包规范与新数据模型，旧包仅通过显式迁移工具导入，不承担永久兼容成本。

## 2. 现有代码真正实现了什么

| 功能 | 已观察到的实现 | 重构判断 |
|---|---|---|
| 页面运行 | CEF 主进程、Renderer、Views 窗口、自定义 scheme | 保留技术路线，重写宿主组织方式 |
| 应用资源 | 根据域名拆分组织和应用名，从 `.yao` 读文件 | 保留包式交付；资源定位和错误处理重写 |
| 应用管理 | 分页、启动、安装、卸载；有 C++ 更新函数 | 有基础流程，未形成完整版本与恢复机制 |
| 系统调用 | `sysInvoke` + Promise + CEF IPC | 保留异步思想，替换数字索引协议 |
| 事件 | `sysSub/sysUnsub`，上下文释放清理 | 保留事件模型，增加范围、权限和背压 |
| 窗口退出 | 窗口登记、关闭请求、退出消息循环 | 保留生命周期集中管理思想 |
| 包格式 | 头、索引、内容、尾，SHA-256/Ed25519 代码 | 不能按现状认定具有有效验签保障 |
| 存储与日志 | SQLite 封装、连接池、日志模块 | 作为候选基础设施，按测试结果取舍 |
| 通用文件/网络 API | 本次未见对应完整 SDK 与系统服务 | 是目标能力，不应算作已交付功能 |
| 浏览器交互 | 取消选文件、抑制 JS 弹窗、阻止 popup 和子框架导航 | 目前更多是禁用，尚非统一原生替代 |

关键证据与影响：

- `apps/src/render/renderer_app.cpp`：在 `OnContextCreated` 注入调用接口，没有看到应用白名单或来源筛选；同时 Renderer 注册应用管理模块。应只注入桥接适配，不在 Renderer 初始化宿主业务服务。
- `apps/src/client/client.cpp`：收到消息后按编号调用 `SysFunc::invoke`，没有看到逐调用的应用权限检查。调用同步进入处理函数，重型文件、打包和数据库操作有阻塞宿主回调线程的风险。
- `apps/src/sys_func/sys_func.h`：函数编号取决于注册顺序。接口契约不应依赖 Browser 和 Renderer 两边模块顺序碰巧一致。
- `apps/src/client/request_handler.cpp`：允许主框架导航；与无来源筛选的接口注入组合后，外部页面获得桥接能力是需要优先消除的风险。这里是代码路径判断，未做利用验证。
- `apps/src/app_manage/yao_pkg.cpp`：加载时 `verifyPackage()` 被注释；`getMetaBytes()` 不覆盖发布者及应用身份字段，文件内容也没有逐文件密码学哈希覆盖。恢复一行验签调用不足以完成可信包设计。
- `apps/src/app_manage/app_manage.cpp`：安装入口同时完成打包与签名；安装移动源文件，更新直接覆盖包。数据库事务无法回滚独立的文件操作；而返回 `expected<bool>` 的 `false` 仍是有值结果，按当前事务封装会走提交路径。
- `libs/storage/src/alkaid_storage/sys/organization.h`、`z-doc/alkaid.sql`：运行时组织表保存私钥。用户运行时与发布者签名权必须分开。
- `apps/src/render/resource_handler.cpp`：域名按最后一个 `-` 拆分，每个资源请求重新打开包，所有读取失败均回退 `index.html`，响应固定 200。应用标识歧义、错误伪装成功和重复解析都应一起解决。
- `apps/src/browser/browser_app.cpp`：桌面 URL 硬编码，桌面创建时传入 `isDesktop=false`，与注释和退出逻辑预期不一致；启动仍调用测试入口 `t()`，但其实际测试调用目前被注释。
- `CMakePresets.json`：沙箱默认关闭。`apps/CMakeLists.txt` 已有沙箱构建分支，但仅有分支不能证明入口接线与发布产物工作正常。

这些问题说明项目适合重建平台边界，而不是继续在 `SysFunc` 上逐项堆能力。

## 3. 产品功能与首期范围

### 3.1 面向使用者

| 区域 | 核心行为 | 必须呈现的状态 |
|---|---|---|
| 我的应用 | 搜索、打开、最近使用、固定、查看详情 | 空列表、加载失败、启动中、运行中、不可用 |
| 安装 | 选择/拖入 YPKG，查看来源、版本、权限，确认安装 | 校验中、不兼容、来源不可信、安装进度、失败原因 |
| 应用详情 | 版本、发布者、占用空间、权限、更新、卸载 | 更新可用、等待关闭、待重启、恢复失败 |
| 运行管理 | 查看窗口与任务、重新打开、结束无响应应用 | 正常、无响应、崩溃、后台任务执行中 |
| 平台设置 | 数据目录说明、主题、缓存、诊断、关于 | 清理范围明确，数据和缓存分别操作 |
| 开发者模式 | 挂载本地 dist、调试、检查 API 和权限 | 明显开发标识，与正式应用数据隔离 |

应用双击打开，键盘 Enter 也可打开；单实例应用再次打开聚焦已有窗口。卸载默认保留业务数据，用户可以明确选择删除。更新新增权限时，先解释变化再授权。

### 3.2 首期能力

首期必须交付：应用安装/更新/卸载、桌面、窗口生命周期、资源服务、SDK/RPC、权限、私有文件、用户选定文件访问、KV 存储、HTTP 请求代理、任务进度、诊断、签名验证、崩溃恢复。

后续按真实应用需要增加：WebSocket、下载续传、通知、剪贴板、应用独立 SQLite API、打印、托盘、自定义协议唤起、受控应用间通信。

首期不做：应用商店后台、支付、账号云同步、任意 shell 执行、第三方原生 DLL 插件、跨平台适配、业务专用服务。后台业务任务与平台开机常驻也不默认开放。

## 4. 总体架构

```text
前端应用 / 平台桌面
        │ 使用类型化 SDK
        ▼
Renderer Bridge（参数传输、Promise、事件、上下文清理）
        │ CEF IPC，不信任传入身份
        ▼
Host Gateway（会话识别 → 契约校验 → 权限 → 配额 → 调度）
        │
        ├─ AppService          安装、版本、卸载
        ├─ RuntimeService      实例、会话、窗口、退出
        ├─ PermissionService   授权、撤销、资源句柄
        ├─ FileService         私有文件、用户选择文件
        ├─ StorageService      应用 KV、平台数据库
        ├─ NetworkService      域名策略、凭据、请求
        ├─ TaskService         进度、取消、恢复
        └─ DiagnosticsService  日志、指标、诊断
                 │
        Windows / SQLite / HTTP 适配层

独立资源链：CEF Resource Adapter → ResourceService → 已验证的只读版本目录
独立开发链：前端构建 → alkaid CLI → 签名 YPKG → 安装入口
```

依赖方向：CEF/Windows 适配层实现核心接口，核心不包含 `CefRefPtr`、V8 对象或 HWND。这样包校验、权限和生命周期状态机可以脱离 Chromium 测试。

服务之间通过明确的接口调用，状态事件用于通知 UI。禁止用全局事件总线隐藏关键安装流程。模块注册需要显式依赖、重复检测、启动错误向上传递和逆序停止。

### 4.1 进程和线程

- Browser Host 拥有平台状态、窗口管理和权限裁决；Renderer 仅处理页面与桥接。
- CEF 的 GPU、网络等子进程由 CEF 自身管理，不自行模拟。
- UI 线程只做窗口及要求在该线程执行的 CEF 操作。
- 文件与网络使用有上限的工作队列；同一应用的安装、更新、卸载串行互斥。
- 平台数据库通过受控写入队列访问，读取按连接策略执行；不跨线程共享未声明线程安全的连接。
- 回调返回前检查会话是否仍有效；导航后旧任务结果不能投递给新页面。
- 首期不要为每个系统模块启动进程。若未来允许原生扩展，必须另行设计隔离 worker 和协议，不能直接加载到 Host。

CEF 的异步 JS 到 Browser 进程模式与此方向吻合，具体回调线程按所锁定版本头文件验证。[CEF 官方使用说明](https://chromiumembedded.github.io/cef/general_usage.html)

## 5. 应用身份、来源与隔离

### 5.1 身份模型

- `appId`：规范化、稳定的应用标识，例如 `com.example.notes`，不由数据库自增 ID 对外表达。
- `publisherKeyId`：受信任签名公钥指纹；展示名称和域名本身不证明发布者身份。
- `version`：应用版本；`packageDigest` 标识实际内容，同版本不同内容默认拒绝覆盖。
- `originKey`：注册表分配的 URL 安全、不变的唯一标识，例如随机生成的字母数字串。
- `instanceId`：一次应用运行实例；`windowId`：窗口；`sessionId`：一次有效文档上下文。

资源 URL 为 `alkaid://<originKey>/index.html`，由注册表解析到应用和固定版本，禁止再从域名切割文件路径。桌面身份由宿主启动登记，不能通过把应用命名为 desktop 获得权限。

### 5.2 隔离规则

每个应用独立 RequestContext、缓存目录和业务数据目录；同应用窗口共享同一个 context，开发与生产 context 分开。不同 RequestContext 不共享 renderer 是 CEF 文档描述的行为，但一个应用仍可能有多个 renderer；不把它简化成“一应用永远一进程”。[CEF RequestContext 接口](https://github.com/chromiumembedded/cef/blob/master/include/cef_request_context.h)

每个浏览器与应用实例在宿主绑定；每次 RPC 校验实际 browser/frame、当前受信 origin、会话代次及对应授权。只在已登记的应用主文档注入桥接；首期不支持 iframe 获得能力。Renderer 即使被攻破，也不能仅靠篡改 appId 扩大权限。

阻止应用窗口导航到其他应用或外部页面；外链通过受控 `shell.openExternal` 打开系统浏览器。关闭原生 popup，新增窗口统一走窗口服务。生产关闭远程调试，禁止通过参数关闭同源策略、证书校验或站点隔离。

生产启用 CEF sandbox，权限代理与沙箱同时存在。沙箱只限制进程，不替代业务授权。当前官方对 M138+ Windows 采用 bootstrap + client DLL 的接入方式有专门要求，需与项目锁定 CEF 包匹配，不能只修改 `USE_SANDBOX` 开关。[CEF 官方沙箱说明](https://chromiumembedded.github.io/cef/sandbox_setup)

## 6. SDK 与通信契约

### 6.1 前端用法

```ts
import { alkaid } from '@alkaid/sdk';

// 取消选择返回 null；访问失败抛出结构化错误。
const file = await alkaid.dialog.openFile({ extensions: ['txt'] });
if (file) {
  const text = await alkaid.files.readText({ handle: file.handle });
  // 前端将 text 展示到编辑器。
}

await alkaid.storage.set('editor.fontSize', 16);
const result = await alkaid.net.request({
  endpoint: 'business', path: '/notes', method: 'GET'
});

const stop = await alkaid.events.subscribe('window.closeRequested', event => {
  // 展示保存提示，再通过带 requestId 的接口答复。
});
```

文件句柄为不透明标识，不返回任意可复用的本机路径作为权限凭据。SDK 只包装协议和类型，不能自行授予权限；普通浏览器环境应明确返回运行时不可用，开发模拟器需显式开启并标识。

### 6.2 方法与事件目录

| 命名空间 | 首期方法示例 | 访问范围 |
|---|---|---|
| `runtime` | getInfo、getCapabilities | 当前应用 |
| `apps` | list、inspect、install、update、uninstall、launch | 桌面管理角色；普通应用不默认开放 |
| `window` | open、focus、close、respondClose | 自己的实例与窗口 |
| `dialog` | openFile、saveFile、message | 当前应用，文件选择绑定操作意图 |
| `files` | readText、writeText、stat、list | 私有区或授权句柄 |
| `storage` | get、set、remove、batch | 当前应用 KV |
| `net` | request | manifest 声明并获准的端点 |
| `tasks` | get、cancel、subscribe | 自己的任务 |
| `permissions` | list、request | 自己的权限；不得越过 manifest |
| `events` | subscribe、unsubscribe | 允许的主题与当前会话 |

平台退出与应用关窗分开：普通应用只关闭自己；桌面才能发起整个瑶光台退出。

### 6.3 传输格式

```json
{
  "protocolVersion": 1,
  "requestId": "8c70...",
  "method": "files.readText",
  "params": { "handle": "fh_..." },
  "timeoutMs": 15000
}
```

请求不接受调用者自报的权限、应用身份或任意执行函数名。宿主补充 `CallContext`，包括应用、实例、会话、来源、截止时间和取消令牌。方法名是稳定协议标识，注册顺序不影响其含义。

```json
{
  "requestId": "8c70...",
  "ok": false,
  "error": {
    "code": "PERMISSION_DENIED",
    "message": "没有读取该文件的权限",
    "retryable": false,
    "traceId": "tr_..."
  }
}
```

成功只返回 `result`，失败只返回 `error`，避免同时存在 Promise 成功和 `success=false` 两套判断。SDK 自动解析 JSON；64 位标识和超出安全整数的大小用字符串，不直接传 JavaScript number。

用单一契约目录描述方法参数、结果、权限、线程、超时和事件，生成 TS 类型及 C++ 校验代码。Bridge 主版本不兼容时拒绝握手，新增可选方法通过 capabilities 查询。

### 6.4 请求与任务语义

- Promise 请求表以 sessionId + requestId 定位；设总量、大小和超时上限。初始建议每会话最多 128 个请求、普通 JSON 消息不超过 1 MiB，压测后调整。
- 导航和关闭清理订阅、句柄、未完成请求；宿主也撤销对应会话，不能只清理 JS 引用。
- 超时不等于操作未发生。读请求可重试；写入、安装通过 operationId 查询结果或幂等键去重，禁止无条件重试。
- 安装、下载等返回 taskId；任务状态为 queued/running/succeeded/failed/cancelled。取消是协作式请求，提交阶段可拒绝取消。
- 事件包含主题、序号和目标范围；高频进度合并，队列有上限。重连后读取状态快照，再接续事件，不将内存事件流当数据库。
- 大文件使用分块流或一次性资源令牌，不通过 JSON/base64 整文件复制；实施字节配额和背压。

## 7. 权限与系统能力

### 7.1 权限计算

有效权限 = manifest 声明 ∩ 平台策略允许 ∩ 用户授权，且还要满足当前资源范围和会话有效性。

| 能力 | 建议策略 |
|---|---|
| 自己的窗口、私有 KV | 安装后可用，受配额限制 |
| 私有文件区 | 应用内授权，不能访问其他应用 |
| 用户文件 | 系统选择框返回单文件或目录句柄，按读/写分别授权 |
| 网络 | 按 endpoint、协议、主机、端口、路径范围限制 |
| 剪贴板/通知 | 按需授权，首期可暂不开放 |
| 应用安装、卸载、平台退出 | 宿主授予的管理角色，仅桌面等受信界面使用 |
| 任意程序执行、注册表写入 | 首期无通用接口 |

授权界面由受信宿主控制，不由请求权限的应用绘制。可用原生对话框；未来若使用 Web 界面，也必须处于独立受信窗口。授权支持单次/会话/持久，撤销时关闭相关句柄并取消可取消任务。私有路径授权校验同时处理规范化、重解析点与操作时竞态，不能只判断字符串前缀。

### 7.2 网络代理策略

选择严格代理模式：业务请求调用 `alkaid.net`，manifest 里将 `business` 映射到实际 HTTPS 服务。平台决定真实目的地、超时、证书策略和凭据，前端不携带平台保存的秘密。

示例 `net.request` 返回 `{status, headers, body}`；HTTP 4xx/5xx 仍是有效 HTTP 响应，DNS、超时和权限失败才作为传输错误。可提供 `requestJson` 帮助业务将非成功状态转成业务异常。

使用 Windows HTTP 适配器实现首期代理，避免同时维护 Chromium Cookie 与原生 Cookie 两套隐式登录状态。业务凭据按应用/端点隔离并受系统保护，OAuth 等复杂登录流程以后单独设计。

统一出口不靠覆盖 `window.fetch` 保证：资源请求、导航、表单、img/script、worker、WebSocket、WebRTC、下载等都是需要验证的旁路。首期资源仅允许本应用已安装内容，远程资源通过显式代理获取；禁用不支持的网络型 Web 能力，并结合 CEF 请求控制、CSP 与沙箱验证策略。无法证明被控制的通道不能算作支持功能。

原生代理逐跳校验重定向；HTTPS 不关闭证书验证；禁止默认访问 loopback、私网与 link-local，确有内网业务时单独声明授权。域名解析和实际连接地址共同校验，处理 DNS 重绑定；认证信息不能跟随重定向发送到别的端点。系统代理、企业代理和 TLS 策略在技术验证阶段测试。

## 8. YPKG v2 与开发工具

### 8.1 包结构

建议继续使用 YPKG 产品名及 `.ypkg` 扩展名，内部采用成熟 ZIP 容器，避免继续自创二进制索引格式。ZIP 只是容器，可信性由独立签名清单保证。

```text
manifest.json
integrity.json
signature.json
assets/index.html
assets/...
```

```json
{
  "manifestVersion": 2,
  "appId": "com.example.notes",
  "name": "便签",
  "version": "1.0.0",
  "publisherKeyId": "sha256:...",
  "runtime": { "apiMajor": 1, "minVersion": "2.0.0" },
  "entry": "index.html",
  "window": { "width": 1100, "height": 760, "minWidth": 720 },
  "instanceMode": "single",
  "permissions": ["storage.kv", "files.private", "files.userSelected.read"],
  "network": { "endpoints": {} },
  "routing": { "mode": "spa", "fallback": "index.html" }
}
```

`integrity.json` 列出所有运行内容的规范路径、原始大小和 SHA-256。签名输入采用带版本前缀、长度编码的 manifest 原始字节和 integrity 原始字节；规范明确 UTF-8 和重复 JSON key 拒绝规则，不依赖不同 JSON 序列化器输出一致。签名文件不签自身，运行内容不允许存在未列入清单的额外文件。

验签必须验证已受信任的公钥。包自带公钥只能证明内容与该钥匹配，不能证明发布者可信。首次导入未知发布者显示指纹和来源并要求显式信任；更新必须保持绑定的发布者身份。密钥轮换需要旧钥签署授权或平台受信恢复流程，不能静默接受新钥。

校验路径拒绝绝对路径、`..`、UNC、盘符、备用数据流、符号链接/重解析点、大小写冲突、重复条目和 Windows 保留名称；设置文件数、解压后总量和压缩比上限。先验签与校验再激活，读取损坏内容不退回首页。

### 8.2 开发与发布

建议 CLI：`alkaid init`、`dev`、`pack`、`verify`、`inspect`。SDK、脚手架和契约文档单独版本化；打包支持任意输出静态 HTML/CSS/JS 的前端框架。

首期开发模式挂载 dist 目录并监听文件变化，不必先做 dev-server 外网转发。开发应用拥有独立 origin/data，显著标识“开发模式”，不允许覆盖受信桌面。

发布者私钥只进入开发机密钥存储或 CI 密钥服务；运行时数据库仅保存公钥、信任状态和吊销信息。平台更新签名与应用包签名是两个体系，不能因某发布者可信就允许其更新瑶光台本体。

## 9. 安装、更新、卸载与恢复

### 9.1 安装状态机

```text
received → verifying → awaitingConsent → staging → ready → committed
                 ↘ failed                 ↘ failed
```

1. 复制用户选定包到 staging，不移动源包。
2. 校验格式、签名、发布者、manifest、兼容性、资源完整性与磁盘空间。
3. 展示安装信息及授权；用户取消则清理 staging。
4. 写入持久化 operation 记录，解压到同卷临时目录并校验。
5. 将内容放入不可变版本目录，完成持久化后标记 ready。
6. 单个数据库事务登记版本、授权和 activeVersion，标记 committed。
7. 提交后发布事件，异步清理临时文件。

**数据库是激活状态的唯一真相。** 不同时维护另一份易失配的 active 指针文件。事务前崩溃留下的版本目录视为未引用内容；事务后崩溃由恢复器核验 activeVersion 引用并修复。文件系统和数据库不可能靠一个普通 SQLite 事务原子提交，必须依赖操作日志、不可变目录和幂等恢复。

### 9.2 更新与回滚

更新先验证同一应用/发布者和版本策略，新增权限先授权。新版本安装到独立目录；已运行实例绑定旧版本，不混用新旧 JS/CSS。首期等待应用关闭后激活更新；可提供“立即关闭并更新”。

保留上一份可用版本。启动健康检查包含资源加载、SDK 握手和 ready 超时；失败时提示恢复旧版本。业务数据迁移另行控制：首期采用加法兼容的数据变化；破坏性迁移必须备份并记录 schemaVersion。回滚程序不代表业务数据可以自动降级，不满足兼容条件时禁止假装回滚成功。

### 9.3 卸载

进入 uninstalling → 阻止新实例 → 请求关闭并等待任务 → 撤销句柄与授权 → 数据库取消激活并标记卸载 → 延迟删除无人使用的资源。文件被占用时记入清理队列，重启重试。保留数据的应用重新安装时仍需验证发布者绑定，不能让同名恶意包接管旧数据。

### 9.4 平台本体更新

首期提供完整安装包覆盖升级，不在运行中的 Host 覆盖 CEF DLL。后续独立 updater 等待主程序退出后切换版本，验证平台签名，失败回滚；平台数据库升级也要有备份和兼容策略。

## 10. 资源加载设计

安装后从已验证、不可变版本目录读取资源，避免每个请求重新解析整个包。资源提供者必须通过宿主登记的 app/session 找到版本，不能由 URL 请求直接打开任意本机路径。

- 正确支持 GET/HEAD、MIME、Content-Length、取消；大资源支持 Range，非法 Range 返回 416。
- 404 是缺失，403 是无权限，500 是内部失败；异常不会返回假 200。
- SPA fallback 仅用于 manifest 声明的页面导航，不用于缺失 `.js/.css`，也不掩盖验签、I/O 错误。
- hash 文件可长缓存；HTML 和激活版本之间有明确失效规则。
- 包内路径统一解码与规范化，禁止双重解码逃逸。
- 默认 CSP 限制脚本和资源到本应用；不允许任意远程脚本或 eval。具体 scheme 标志按所锁定 CEF 版本验证，不添加绕过 CSP 的配置。
- 用户文件若需在 img/video 中显示，使用范围限定、可撤销的短期资源令牌，不暴露 `file://` 或真实磁盘路径。

## 11. 数据与目录

通过 Windows 已知目录 API 定位用户数据根目录，不再相对可执行文件任意落盘。下面是逻辑结构：

```text
Alkaid/
  platform/platform.db
  packages/<appId>/<version>-<digest>/
  data/<appId>/files/
  data/<appId>/kv.db
  profiles/<originKey>/
  staging/<operationId>/
  recovery/
  logs/
```

平台数据库建议表：

| 表 | 关键内容与约束 |
|---|---|
| publishers | keyId 唯一、公钥、信任/吊销状态 |
| apps | appId 主键、originKey 唯一、publisherKeyId、activeVersionId、状态 |
| app_versions | appId+version 唯一、digest、manifest、路径、验证状态 |
| grants | appId、能力、范围、期限、授权版本，禁止重复授权记录 |
| operations | operationId、类型、应用、阶段、失败原因、恢复数据 |
| preferences | 平台设置，带 schema 版本 |
| schema_migrations | 迁移编号、执行时间、校验摘要 |

实例和会话以内存状态为准，崩溃后不能把数据库中上次“运行中”当成真实存活。诊断可保存会话历史。

SQLite 使用显式迁移、约束、参数绑定和短事务；WAL 模式、超时和备份流程需作为统一配置验证。平台库不向应用暴露 SQL；应用 KV 与平台数据分离。后续若提供 SQL，只允许应用自己的库，并限制查询时间、结果大小和磁盘占用。

## 12. 桌面交互与生命周期

桌面采用清晰的应用启动器布局：左侧“我的应用 / 运行中 / 设置”，主区应用列表或卡片，顶部搜索和“安装应用”。应用详情使用侧栏或独立页面，避免在卡片上堆放所有管理按钮。主题遵循系统，支持高 DPI、键盘导航和清晰焦点。

首屏不做商店、资讯、统计大屏或业务内容。用户的主要路径是“找到应用 → 打开 → 使用”，管理操作按需出现。

生命周期建议：installed → starting → running → closing → stopped，另有 crashed/disabled。启动回执区分“已接受启动”和“页面 ready”，不能投递一个 CEF task 就向界面宣称应用已启动成功。

窗口关闭统一发出带 requestId 的 closeRequested。应用可保存或请求取消；宿主设等待期限，无响应时展示“继续等待/强制关闭”。平台退出依次拒绝新任务、请求各窗口保存、等待任务、关闭浏览器，最后执行 CefShutdown。不能无限等待桌面 JS，也不能忽略所有 beforeunload 回调。

桌面崩溃提供重新加载或原生最小恢复窗口。即使桌面资源损坏，仍应能退出平台、查看错误和修复安装，不能让唯一管理入口完全依赖一个可损坏的应用包。

目录表达职责，不要求每个目录单独 DLL。首先按 CMake target 建立依赖边界。桌面前端可用团队熟悉的 Vue 或 React，但平台 SDK 不依赖它们，当前没有必要为 UI 框架做技术迁移。

| 旧内容 | 处理 |
|---|---|
| CEF 初始化、窗口示例 | 作为参考移植，重新验证线程与退出 |
| SysInvoke、SysPubsub | 参考生命周期清理思路，协议和存储结构重写 |
| AppManage | 用状态机服务替代，不把旧函数逐个搬过去 |
| YaoPkg | 旧格式只用于迁移读取；新包采用独立实现 |
| DB/日志/工具 | 逐项复用，经测试证明后纳入；不继续扩张通用 ORM |

错误采用 `tl::expected<T, Error>`；第三方异常在适配边界捕获转换。中文用户提示、日志描述与稳定英文错误码分离。敏感参数、文件内容、令牌和私钥不进入默认日志。

## 14. 验证、性能与发布要求

### 14.1 必须验证的场景

| 类别 | 验收要求 |
|---|---|
| RPC | 非法参数、超大报文、伪造身份、重复请求、乱序结果、导航后迟到结果均可控 |
| 权限 | 应用 A 无法读 B 数据；普通应用无法安装/卸载别的应用或退出平台 |
| 包 | 篡改任意资源、替换身份、错误钥、路径穿越、解压炸弹、重复路径全部拒绝 |
| 恢复 | 安装各持久化阶段强制结束后重启，恢复到旧版可用或新版完整可用 |
| 网络 | 直接 fetch/img/form/worker/WebSocket/WebRTC 等旁路、重定向及私网目的地测试 |
| 生命周期 | 单实例聚焦、多窗口关闭、保存取消、Renderer 崩溃、桌面崩溃、强制退出 |
| 数据 | 更新保留数据、卸载选择生效、撤销权限立即失效、备份可恢复 |
| 资源 | 正确 MIME/404/Range/取消；缺失 JS 不返回 HTML；版本切换不混资源 |
| Windows | Win10/11 目标版本、非 ASCII 路径、高 DPI、多屏、低磁盘、文件占用、代理环境 |

纯核心逻辑做无 CEF 单元测试；跨进程桥接和权限做真实 Host 集成；桌面和样例应用做端到端。包解析加入模糊测试，安装恢复加入故障注入。生产沙箱启用状态要在发布产物中验证，不能以配置值替代。

### 14.2 性能预算（初始目标，非测量结果）

以 4 核 CPU、16 GB 内存、SSD 的 Windows 测试机为基准，记录明确 OS/CEF 版本、包大小和冷热启动条件：桌面冷启动到可交互目标 p95 ≤ 3 秒；小型应用热启动 p95 ≤ 1 秒；无 I/O RPC 往返 p95 ≤ 20 ms。安装/大文件不能产生超过 50 ms 的宿主 UI 阻塞任务。

CEF 内存基线先实测再设预算，记录空桌面与 1/5/10 个应用的工作集、私有字节和增长趋势，不承诺不现实的固定低内存。限额初值通过压测修订；不能为降内存关闭隔离。

构建锁定 CEF 版本、下载校验和及 vcpkg baseline。开发和发布配置分离；CEF 下载从隐式 configure 副作用改为显式依赖准备步骤。发布产物包含宿主、CEF 必要资源、桌面包、运行库和许可证；在无开发环境的干净机器验证。

## 15. 实施路线与交付门槛

按小团队 2～3 人给出粗略工作量窗口，不作为承诺日期；先完成技术验证，再估算开发计划。

| 阶段 | 主要交付 | 完成门槛 | 初始估算 |
|---|---|---|---|
| P0 可行性验证 | sandbox 启动、独立 context、自定义 scheme、网络旁路原型 | 两个应用隔离，生产接入路线确定 | 1～2 周 |
| P1 运行骨架 | Host/Renderer、SDK、RPC、身份、权限、资源、示例应用 | 打开应用、受控调用、导航回收闭环 | 2～3 周 |
| P2 应用交付 | CLI、YPKG v2、验签、安装/更新/恢复、注册表 | 篡改拒绝、故障注入恢复通过 | 2～3 周 |
| P3 产品闭环 | 桌面、文件、KV、HTTP、任务、窗口关闭 | 用户安装并完成实际应用操作 | 2～3 周 |
| P4 发布加固 | 压测、兼容、故障诊断、迁移、安装包 | 干净 Windows 环境验收通过 | 2～3 周 |

阶段有可交叠工作但不能简单相加当成可靠工期。首个演示纵向切片建议做“便签应用”：安装 → 打开 → 读取用户选定文本 → 编辑 → 保存到授权文件 → 私有设置持久化 → 关闭确认 → 更新后数据仍在。这能验证平台主张，而不只验证空页面能启动。

迁移先做只读清点并备份旧包和数据；旧格式导出前端资源，补 manifest，由真实发布者重新签名。旧表里的发布者私钥不能自动迁入运行时新库，也不能把历史公钥自动设为受信。新旧数据目录隔离，达到验收后再由用户决定切换；本方案不包含实际删除旧代码或数据的操作。

## 16. 主要决策、风险和后续确认

| 决策 | 推荐默认 | 代价或需验证点 |
|---|---|---|
| 继续 CEF | 是 | 保留部署体积与升级维护成本；先验证沙箱构建 |
| 换 WebView2 / Electron | 本轮不换 | 换引擎仍需重建同一套身份/权限/包机制；有明确部署目标再做单独评估 |
| 支持旧包 | 显式迁移 | 旧应用需补清单与重新签名，避免长期兼容分支 |
| 运行包方式 | 校验后解压、版本目录只读 | 占用更多磁盘，资源加载与恢复更简单 |
| 系统操作入口 | 显式 SDK | 旧前端需改 API，无法“零修改代理所有浏览器行为” |
| 网络 | 严格受控出口 | 远程媒体、OAuth、WebRTC 等需独立能力设计 |
| 本机系统权限 | 普通用户运行 | 涉及管理员操作另行设计，不提升整个 Host |
| 数据迁移 | 首期仅兼容性迁移 | 复杂破坏性 schema 更新需要额外协议 |

当前方案假设主要承载内部或受信发布者应用，但仍按应用内容可能出错或被篡改设计边界。若要运行公开市场的任意第三方应用，需追加发布者治理、吊销分发、独立安全审计和运营机制。

真正影响下一轮细化的产品问题：预计同时运行多少应用；是否必须支持离线；是否需要长驻后台；是否必须连接局域网设备；是否已有必须迁移的实际应用和用户数据。以上不阻止本方案评审，答案会影响容量、网络策略和迁移范围。

建议先批准的是架构边界与首期范围，再以 P0 的可运行证据锁定实现细节。最终验收应证明：一个普通前端应用只依赖 SDK 就能完成真实桌面工作，同时无法越过自己的权限、资源与生命周期边界。
